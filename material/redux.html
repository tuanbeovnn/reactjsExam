    Motivation

    • More state changes in single page JavaScript applications than ever before
      • Managing the state is hard
    • There is a lot of complexity and managing complexity is hard
      • Especially as we combine mutations and asynchronicity
    • React helps in DOM manipulation
      • State management needs something else

    Predictable mutations

    Redux attempts to make state mutations predictable by imposing restrictions on how and when updates can happen.

    Following the footsteps of
    Flux , CQRS and Event Sourcing
    • More here

    Concepts

    • State is described as a plain object
      • To change something in the state, an action (also a plain object) is dispatched
        • Actions reveal what happens in the application
        • Finally, a reducer is used to create a new state
          • It takes an action as an argument and returns the next state
          • Smaller reducers can be combined to be a bigger reducer

        https://redux.js.org/introduction/core-concepts

      Three Principles

      • Single source of truth
        • The state of your whole application is stored in an object tree within a single store.
      • State is read-only
        • The only way to change the state is to emit an action, an object describing what happened.
      • Changes are made with pure functions
        • To specify how the state tree is transformed by actions, you write pure reducers.
      • https://redux.js.org/introduction/three-principles

      Actions

      • Payloads of information that send data from your application to your store
      • Plain JavaScript objects
      • Action types are usually defined as constants
      • Action creators return actions
      • Actions are dispatched to change the state
      • Describe what happened
                         
            //action type
            const ADD_TODO = 'todos/todoAdded'
            //what an action object would look like
            {
              type: ADD_TODO,
              payload: 'Build my first Redux app'
            }

            //action creator (returns the action)
            export function addTodoAction(payload) {
              return { type: ADD_TODO, payload }
            }

            //dispatch action
            store.dispatch(addTodoAction('Build my first Redux app'))

      Reducers (1/4)

      • Specify how the application's state changes in response to actions sent to the store
      • The state is reduced based on an action and a new state is returned
      • Design the state shape first
        • It should be a single tree
        • You will probably need to store e.g. data and UI state information
          • Keep these as separate branches
        • The state is kind of like a database
        • It is suggested to not have any nesting and to store entities so that they have an ID as a key

      Reducers (2/4)

      • A pure function that takes the previous state and an action, and returns the next state
        • (previousState, action) => newState
      • Never do these inside a reducer to keep it pure
        • Mutate its arguments
        • Perform side effects like API calls and routing transitions
        • Call non-pure functions, e.g. Date.now() or Math.random()

      Reducers (3/4)

      • We don't mutate the state
      • We return the previous state in the default case
               
            function todoApp(state = initialState, action) {
              switch (action.type) {
                //handle an action
                case ADD_TODO:
                  //optionally use the spread operator to copy
                  //enumerable properties from one object to another
                  //e.g. return {...state, todos: [as below]}
                  return Object.assign({}, state, {
                    todos: [
                      ...state.todos,
                      {
                        text: action.text,
                        completed: false
                      }
                    ]
                  })
                //case XYZ: would handle another action
                //return the default state
                default:
                  return state
              }
            }

      Reducers (4/4)

      We can split the reducers into smaller pieces and then combine them by hand or using combineReducers()
        • The resulting reducer calls every child reducer, and gathers their results into a single state object
         
          function visibilityFilter(state = SHOW_ALL, action) {
            switch (action.type) {
              case SET_VISIBILITY_FILTER:
                return action.filter
              default:
                return state
            }
          }
          function todos(state = [], action) {
            switch (action.type) {
              case ADD_TODO:
                return [
                  ...state,
                  {
                    text: action.payload,
                    completed: false
                  }
                ]
              case TOGGLE_TODO:
              //content of TOGGLE_TODO omitted
              default:
                return state
            }
          }
          const todoApp = combineReducers({
            visibilityFilter,
            todos
          })

      Store (1/2)

      • The store brings the actions and reducers together
      • You will only have a single store in a Redux application
      • The store
        • Holds application state
        • Allows access to state via getState()
        • Allows state to be updated via dispatch(action)
        • Registers listeners via subscribe(listener)
        • Handles unregistering of listeners via the function returned by subscribe(listener)

      Store (2/2)

         
            //Create the store
            //You may optionally specify the initial state 
            //as the second argument to createStore()
            import { createStore } from 'redux'
            const store = createStore(todoApp)

            console.log(store.getState())

            // Every time the state changes, log it
            // Note that subscribe() returns a function for unregistering the listener
            const unsubscribe = store.subscribe(() => console.log(store.getState()))

            // Dispatch some actions
            store.dispatch(addTodoAction('Learn about actions'))

            // Stop listening to state updates
            unsubscribe()

      Data flow

      • Strict unidirectional data flow
      • The data lifecycle in a Redux app:
        1. You call store.dispatch(action).
        2. The Redux store calls the reducer function you gave it.
          • The store will pass two arguments to the reducer: the current state tree and the action. The reducer then computes the next state
        3. The root reducer may combine the output of multiple reducers into a single state tree.
        4. The Redux store saves the complete state tree returned by the root reducer.

      Actions when calling an asynchronous API

      • Usually, for any API request you'll want to dispatch at least three different kinds of actions:
        • An action informing the reducers that the request began.
          • This will result in setting a loading state.
        • An action informing the reducers that the request finished successfully.
        • An action informing the reducers that the request failed.
      • You can use separate types or a status field to represent these.
         
          { type: 'FETCH_POSTS_REQUEST' }
          { type: 'FETCH_POSTS_FAILURE', error: 'Oops' }
          { type: 'FETCH_POSTS_SUCCESS', response: { ... } }
          //or
          { type: 'FETCH_POSTS' }
          { type: 'FETCH_POSTS', status: 'error', error: 'Oops' }
          { type: 'FETCH_POSTS', status: 'success', response: { ... } }

      Async Action Creators with Redux Thunk

      • Using Thunk, an action creator can return a function instead of an action object
        • When an action creator returns a function, that function will get executed by the Redux Thunk middleware.
          • This function doesn't need to be pure; it is thus allowed to have side effects, including executing asynchronous API calls.
          • The function can also dispatch actions—like those synchronous actions we defined earlier.
      Full example here 
      
            function fetchPosts(subreddit) {
              return dispatch => {
                dispatch(requestPosts(subreddit))
                return fetch(`https://www.reddit.com/r/${subreddit}.json`)
                  .then(response => response.json())
                  .then(json => dispatch(receivePosts(subreddit, json)))
              }}
            //call using store.dispatch(fetchPosts('reactjs'))
          
      
            //Actions and reducer

            const REQUEST_POSTS = 'REQUEST_POSTS'
            const RECEIVE_POSTS = 'RECEIVE_POSTS'
            
            function requestPosts(subreddit) {
              return {
                type: REQUEST_POSTS,
                subreddit
              }
            }
            
            function receivePosts(subreddit, json) {
              return {
                type: RECEIVE_POSTS,
                subreddit,
                posts: json.data.children.map(child => child.data),
                receivedAt: Date.now()
              }
            }

            function posts(
              state = {
                isFetching: false,
                didInvalidate: false,
                items: []
              },
              action
            ) {
              switch (action.type) {
                case REQUEST_POSTS:
                  return Object.assign({}, state, {
                    isFetching: true,
                    didInvalidate: false
                  })
                case RECEIVE_POSTS:
                  return Object.assign({}, state, {
                    isFetching: false,
                    didInvalidate: false,
                    items: action.posts,
                    lastUpdated: action.receivedAt
                  })
                default:
                  return state
              }
            }
